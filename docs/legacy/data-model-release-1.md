# Release 1 — Durable data model

This refines macro C1/C2/C7/C8/C9 records for the eight stories. SQLite is the only domain store; private credential files hold secrets. No valuation, portfolio, MCP or historical-cutoff entities are implemented. SQL below is a schema contract expressed as columns/constraints, not an implementation migration.

## Representation rules

IDs are server-generated UUID text, foreign keys are enabled, timestamps use UTC RFC3339 with microseconds. Source date-only values stay ISO dates with precision metadata; they are never falsely promoted to exact UTC times. Decimal quantities use canonical decimal TEXT and an explicit unit/currency/share basis; JSON serializes them as strings. Parse provider numbers as Decimal. Invalid/NaN/infinite values become rejected fields with reasons; no floating-point financial storage or rounding. Hashes use SHA256 of canonical nonsecret content. JSON columns require json_valid and versioned typed validation; they do not replace relational foreign keys for required joins. Application code validates enums before writes and SQL CHECK constraints enforce the same admitted sets.

Immutable observations/versions/facts/checks/audit are append-only via repositories. Mutable rows (coverage, job/operation, pointers and slots) have integer revision>=0 and optimistic updates. Never delete records referenced by other records. DELETE is not exposed. Every acknowledged durable write shares its transaction with safe audit; a read cannot refresh data. IDs and DTO keys use contract Vocabulary; SQL-only columns are internal implementation names, not additional public fields.

Version/checkpoint multi-reference collections use typed relational join tables (observation/version/evidence/window-period references), with FK enforcement. R1 realizes `window_anchor_evidence`, `dataset_check_refs` and `checkpoint_refs` as a kind column plus one nullable foreign-key column per admitted kind: a CHECK per kind makes exactly the named column non-null, a unique index covers parent, kind and target, and a referenced target cannot be deleted. Small safe metadata and gap details may be JSON. As built in 1.2: `annual_windows.resolution_reason` holds JSON with `anchor_year`, `anchor_kind`, `published_year`, `unobserved_years` and `timing_limitations` (the last two added in US3); `statement_versions.basis` and `current_statement_versions.basis` hold the binding version; `source_observations.source_path` holds the endpoint ID and a call's own row has no period and `availability_basis` `retrieval-time-only`, since a whole response has no publication time of its own; a supplied statement filing date (corrected at build, 1.2, US5) has one further row per accepted version, with the same acquisition and raw hash as the version's primary call, the `period_id`, `published_at`, `published_precision` and `availability_basis` `filing-date`, found through that acquisition and period and named in the version's audit `new_refs` as `publication_observation_id`; facts, `statement_version_observations` and check references stay on call rows, and a period with no supplied date has no such row; `dataset_coverage.gaps` omits evidence-only reasons (`exact-duplicate`, `not-annual-event`), which stay on `dataset_checks.gaps`. A reverted correction whose hash matches an older version moves the pointer back to that version instead of inserting a duplicate. As built in 1.2 (US4): `requests.result_receipt` holds the `job_id` and `operation_id` for replay; a cancel request has a `requests` row and no `operation_requests` row; `jobs.terminal_outcome` holds the overall data outcome. As built in 1.2 (US8): a retry request is stored like a cancel request; a retry clears `jobs.terminal_outcome`, `execution_failure` and `cancel_requested_at`, which each ended attempt and the audit keep; a retained `job_items` row starts `finished` with the kept `checkpoint_id`, so it shares the checkpoint with the earlier attempt's item and has no `dataset_checks` row of its own. The detailed SQL migration is an implementation artifact; it must realize these uniqueness, state and atomicity constraints, not change the model.

## Coverage, dates and lifecycle

Each statement's spec catalog entries resolve to a value on an explicit observed basis or a gap. A field absent in a corrected valid response is a new missingness observation, not a silent carry-forward; prior accepted value remains inspectable in its older version. Wrong-identity/outer-shape failure accepts no candidate values and preserves the current pointer. A partially valid response publishes its valid fields and gaps under a new version only after domain validation. All three datasets use the same resolved annual window; out-of-window rows may establish evidence but cannot fill an internal missing requested period.

Changed semantic content advances content_revision and check_revision and last-content-change; unchanged successful check advances check_revision/last-success only. First accepted content is changed with no predecessor. A successful empty/excluded earnings lookup advances check_revision and last-success, preserving the older event as explicitly dated prior evidence; its new timing limitation must be used for operation aggregation. Failure changes last-attempt and failure history only. Superseded evidence remains on its attempt and does not replace newer coverage. Atomicity also covers checkpoint, publication receipt and audit.

Read/write behavior is separate for every lifecycle: active jobs are readable and accept permitted cancel; failed/interrupted jobs remain readable and accept explicit retry; done/cancelled remain readable and refuse retry; rejected acquisitions remain readable as evidence and cannot become accepted values; older versions remain readable and immutable; missing credentials preserve reads but block dependent network checks; unavailable storage returns a failure, never an empty dataset. Jobs' transition table and refresh's ordered aggregate table are normative.

## Startup and ownership

No database owns raw vendor keys. Private immutable files and SQLite active pointers use the staged protocol in setup-authority.md; there is no claim that filesystem and database operations form a single atomic transaction. Initial enrollment, rotation, recovery and credential configuration share this pattern. Sessions/CSRF are in memory and never inspected. Local filesystem ownership is the recovery authority; a browser cannot acquire it.

SQLite has one process owner and short write transactions. Test concurrency with deterministic interleavings even though production has one refresh worker: later separate operations, replays and future consumers must not bypass revision guards. Backups remain private and never tracked. Migration and recovery tests use synthetic data and preserve logical IDs/history.

## Scope and verification

R1 stores the annual catalog and operational policies, not all investigated input families. No company-quality decision, computed ROIC, normalized earnings, policy editing or point-in-time sufficiency is claimed. Follow [quickstart.md](quickstart.md) for the validation matrix and contracts for per-seam tests. At /tasks, test-file mappings are trued and the declared obligation set must remain complete.
